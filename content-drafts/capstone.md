# Module: Capstone

*Combine design, data, forms, authentication/API usage and deployment in a realistic project. Builds on Deployment & Delivery.*

This module is different from the ones before it. There's no new syntax to learn — the goal is combining everything from Developer Orientation through Deployment & Delivery into one real, complete project. The two lessons here are about planning and scope, not new technical concepts; the actual learning happens in building the project itself.

### Lesson 1 — Planning Your Capstone

**Why this matters**

The single most common way a capstone project goes badly isn't a lack of skill — it's scope. Something that sounds simple in one sentence ("a task tracker with teams and notifications") is often three or four separate projects stacked together. Planning honestly, before writing code, is what keeps this project finishable in the time you actually have.

**The core idea**

Pick something small enough to genuinely finish, that still touches every skill from this path:

- A page or two of real UI (semantic HTML, responsive layout — from HTML Foundations and CSS).
- Real data, fetched or stored somewhere (Data & Forms).
- At least one form with server-side validation (Data & Forms, Zod).
- Clear component structure (React Foundations, Next.js Core).
- Deployed and actually reachable by a URL (Deployment & Delivery).

A strong capstone is usually a small, complete thing — not a big, half-finished one. "A bookmarking app where you save links with tags and search them" is a better scope than "a social network," even though the second sounds more impressive on paper. Finished and working beats ambitious and incomplete, every time a mentor is the one reviewing it.

**Try it yourself**

Write a one-paragraph description of what you want to build, then list every skill from this path it would actually exercise. If a skill from the path (forms, data fetching, deployment) isn't touched by your idea at all, either the idea needs adjusting, or that's a deliberate, known gap — either is fine, as long as it's a decision you made on purpose rather than something you didn't notice.

**A mistake beginners actually make**

Picking a project scoped for a team of five, then trying to build all of it alone in the time available. If your plan requires user-to-user messaging, multiple user roles, real-time updates, *and* payments, that's several capstones, not one — cut it down before you start, not three-quarters of the way through when it's a much harder decision to make.

### Lesson 2 — Requirements & Rubric

**Why this matters**

A clear, explicit bar for "done" is what makes a mentor's review fast and fair, and what stops a capstone from quietly expanding forever because there's always one more feature that could be added.

**The core idea**

Your capstone will be reviewed against the same requirements as every other assignment on this path — the difference is scale and integration, not the review process itself. What "done" looks like here:

- **Real, working functionality** — not a mockup, not hardcoded fake data standing in for something dynamic.
- **At least one form with genuine server-side validation.**
- **Deployed to a real, working URL**, with environment variables properly configured, not just running locally.
- **A README** explaining what the project does, and — importantly — what you'd build next if you kept going. Nobody expects a capstone to be a finished commercial product; a clear account of its current scope and its natural next steps is a genuinely stronger signal of understanding than pretending it's complete.

**Try it yourself**

Before writing any code, write your project's README first — what it does, what it doesn't do yet, and how to run it. Writing this *before* building tends to sharpen the scope decision from the last lesson far more than writing it after, once you already know exactly what got built.

**A mistake beginners actually make**

Treating "it's deployed" as the finish line and skipping the README, or leaving it as the default framework-generated placeholder text. The README is often the very first thing anyone reviewing your work actually reads — it's setting the frame for everything that follows it.

## Assignment: Capstone Project

**Instructions:**

Plan, build, and deploy one real project that combines what you've learned across this entire path. This is the final assignment before you're considered ready for independent work.

**Requirements:**
- Genuinely your own scope — not a copy of one of this path's earlier assignments with only cosmetic changes.
- At least one page of real, responsive UI.
- Real data — fetched from an API, or your own simple backend (a database is a strong choice here, but a well-justified simpler approach is fine too).
- At least one form with server-side validation.
- Deployed to a real, working URL.
- A README describing what it does, how to run it, and what you'd build next.

**What to submit:**
- A GitHub repo link.
- A deployed URL.
- Your README, as part of the submission (link to it directly, or paste its content into your notes).
- In your notes: what you'd do differently if you started this project over today, now that it's finished. This is the single most useful question to answer honestly — it's usually where the real learning from a capstone actually shows up.
